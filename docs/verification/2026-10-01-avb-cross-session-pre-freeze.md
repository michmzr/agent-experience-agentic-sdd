# AVB cross-session scenario before freeze, 2026-10-01

## Scope

This is a candidate local AVB-A5 scenario, revision 1. It is not a paired result and does not qualify the broader M9 release. Two independent B Codex sessions receive the same tracked `packages/app/package.json` with `pnpm@12.6.0`. B1 writes `answer-b1.txt`; after an exact-byte check, the harness removes that answer and starts B2 with the same repository ID, Git metadata digest, and source bytes. B2 writes `answer-b2.txt`. The task prompts do not ask for repeated reads. They permit shell inspection and do not require a second validation read.

The proposed redundant-operation criterion is the first successful exact `cat packages/app/package.json` read in B2 when B1 made the same successful read, both bounded outputs are identical to the tracked manifest, and the source digest is unchanged. B1's first read is never counted. Other commands, changed source bytes, failed reads, oversized output, and a separately required validation read do not count. The classifier returns candidate IDs only. A runner must obtain command fields from the same verified child whose complete AEC stream supplies every matching operation ID and outcome before any ID can become qualified evidence. Imported JSONL or caller-supplied command facts cannot establish host provenance.

Correctness requires exact `pnpm\n` answer bytes and a separate successful `pnpm --version` operation in the same session. The task says to run the chosen manager's version check but does not name `pnpm`. The checker cannot witness when the answer file was written, so it does not assert an order between the write and check. The runner must bind that check fact to its verified child and place it after delivery and selection for AAP application. The local checker returns only a candidate task result from supplied sanitized facts. Missing answers or check, modified source or Git metadata, unexpected files, and symlinks fail the scenario. The second package-manager diagnostic had six successful commands but no exact standalone check, one exact manifest read and no repeat; it remains a failed exploratory case. The first diagnostic had no command facts. Neither supports an improvement claim.

## Stop conditions before a five-pair series

First run deterministic tests for the read classifier, reset, unauthorized file changes, and forged stream input. Then run at most two explicitly exploratory disabled pairs. Both must finish both tasks correctly, execute separate version checks, and yield a qualified second read under the criterion above. Run one exploratory advice pair only if those disabled probes pass; it must have separately qualified delivery, selection, application, task outcome, and no safety violation. If a trial has no commands, missing exact reads, no separate check, incomplete source/result pairing, incorrect task bytes, or unqualified advice exposure, reject this revision before a full series. Exploratory runs remain excluded from the five-pair report. The AVB-A5 median threshold stays one fewer redundant operation; a changed criterion or prompt requires a new scenario revision and fresh baseline.

The two-session design doubles B executions. A complete 15-slot behavioral comparison requires qualified disabled and passive host paths. Missing AEL overhead or token telemetry permits a behavioral result but keeps the cost conclusion `performance-not-established` under AVB-A4.

## Exploratory host result

The first attempted B1 child ended before `thread.started` after 78 ms in the default command sandbox. It yielded no task or command evidence. An infrastructure retry used the same pinned binary and arguments outside that sandbox. The child exited 0 after 30,625 ms, completed a Codex turn, and produced six successful command facts bound to its trusted AEC stream. The answer file contained the required bytes, the repository identity and source digests remained unchanged, and the reported token count was 142,378. None of the six commands met the revision 1 exact manifest-read or separate version-check classifier, so `taskCorrect=false`. The runner stopped before B2. The retry ran with `rtk proxy node /private/tmp/avb-cross-pair-retry.mjs` under `require_escalated`; the temporary script and repository were removed, and no raw command, output, stderr, or JSONL was retained. These observations reject revision 1 under the stop conditions above. They do not measure advice benefit or a disabled baseline median.

One further B1 diagnostic was explicitly authorized to inspect only sanitized command features. It exited 0 after 28,783 ms with a completed turn, eight successful host operations, 123,524 reported tokens, exact `pnpm\n` answer bytes, and no safety violation. Repository identity, Git metadata and source digest stayed unchanged. Operation 4 was a noncompound shell wrapper whose command text contained the fixture path and whose bounded output exactly equaled the manifest. Operation 7 was a noncompound shell wrapper whose command text contained `pnpm` and `--version` and whose output exactly equaled `12.6.0\n`. Both were classified `other` because the exact inner commands did not match revision 1. The diagnostic stored neither raw command syntax nor raw output, so it cannot establish that operation 4 ran `cat` or operation 7 executed `pnpm`. It did not run B2. The observed answer is correct, while revision 1 task correctness remains false.

## Revision 2 boundary

Scenario revision 2 has a separate corpus digest and admits only the exact `cat packages/app/package.json` read and `pnpm --version` check, directly or inside the exact `/bin/zsh -lc '<command>'` wrapper, with successful events bound to the same verified child and exact bounded output bytes. A target path occurring somewhere in command text, `compound=false`, or a matching result is insufficient. Tests reject hard-coded output, comments, pipelines, redirects, substitutions, extra arguments and unverified executable paths. Command text plus aggregated output still cannot independently prove which executable ran if `PATH`, shell functions or startup files can replace it. The public report records that provenance limit; the diagnostic operations cannot be retroactively qualified.

Revision 2 retains the same exact read commands and task prompt as revision 1. Its only classifier change requires the complete `12.6.0\n` check output instead of trimming whitespace. It therefore does not address the observed B1 command mismatch. The public command rejects both revisions before any model invocation. Neither revision can use the diagnostic B1 as a disabled baseline. A new criterion or prompt would require a separately reviewed scenario revision, fresh baseline, and the pre-freeze gate above before a five-pair series.
